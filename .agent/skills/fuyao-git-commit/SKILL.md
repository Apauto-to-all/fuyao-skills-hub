# Git 提交消息规范

在 fuyao 项目仓库下创建 git 提交时强制执行本规范，保证提交历史可读、可追溯、可回滚。

## 何时使用

* 用户**明确要求**提交（"提交"、"commit"、"保存这次改动"）时
* 将已完成的改动写入版本库时
* **不主动提交**：用户未要求时只完成代码修改，把提交决定权留给用户

## 提交前检查

* 注释禁项扫描：`git diff --staged` 的新增注释行中不得出现变更历史/辩护词（为什么删除、为什么移动、已迁至、原先在、不再属于等）与出处/对标话语（参考、对齐、借鉴等）；命中者改写为对当前代码的现在时陈述，不改不许提交

## 格式

```
<类型>(<范围>): <描述>

<正文：空一行后书写，按模块/动机分条说明>

<脚注：可选>
```

## 类型

| 类型 | 用途 |
| ------ | ------ |
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `docs` | 文档更新 |
| `style` | 代码格式（不影响功能） |
| `refactor` | 重构（既不修复 bug 也不添加功能） |
| `test` | 添加或修改测试 |
| `chore` | 构建过程、辅助工具、依赖变更 |
| `perf` | 性能优化 |
| `ci` | CI 配置变更 |
| `build` | 构建系统或外部依赖变更（Cargo.toml、package.json） |
| `revert` | 回滚之前的提交 |

取**主要变更**的类型。一次改动里 refactor 为主、附带小 fix，则用 `refactor`。

## 范围（可选）

影响的模块或子系统，用小写短词，对应 crate 名或模块名：

* 单 crate 内：`config`、`agent`、`mcp`、`tools`、`session`、`provider`、`engine`、`guard`
* 跨 crate / 跨模块：**省略范围**，或用概括词（如跨多个工具用 `tools`）

判断标准：读者看范围就能预判 diff 涉及哪里。拿不准就省略。

## 标题规则

1. **中文**撰写（标题与正文均使用中文）
2. **命令式语气**：说"迁移配置"而非"迁移了配置"；"移除字段"而非"移除了字段"
3. **不超过 72 字符**（中文按字数，含类型与范围前缀）
4. **句末不加标点**（无句号、无冒号收尾）
5. 类型 + 范围前缀与描述之间用 `:` 分隔
6. 标题已能完整表达时，正文可省略

## 正文规范（可选）

标题之外需补充**为什么**改、**改了什么**时写正文：

1. 标题与正文之间**空一行**
2. 每行不超过 72 字符，超长折行
3. 按**动机 → 内容**组织：先讲为什么改（背景/问题），再列具体改了什么
4. 多模块改动用分条（`-` 或换行）按模块/主题列出
5. 解释 **Why**（为什么这样改），而不是重复 **What**（diff 已经能看出 What）

## 整合提交原则

**多个文件 / 多个模块的修改必须整合为一个提交消息，禁止拆分成多个提交。**

工作区与暂存区的全部改动是一次逻辑变更，应作为一个原子提交入库。规则：

1. **标题**概括整体变更方向，类型取主要变更类型，范围按上文取舍
2. **正文**按模块 / 主题分条列出具体修改内容
3. **范围**涉及多个模块时省略，或用概括性词汇

### 整合提交示例

一次配置系统重构同时改了 6 个文件（api/config、agent/context、lib、init、tool_runner）：

```
refactor(config): ToolRunnerConfig 迁入 config 模块，移出 AgentContext

工具并发策略属于本地配置文件范畴（[tools.runner]），不应作为运行时上下文
被构造/修改。类型从 agent/context.rs 迁至 config/tools.rs，AgentContext
删除 tool_runner_config 字段，消费点 tool_runner 直接读 get_config().tools.runner，
init_engine 不再装配该字段。
```

## 边界

* **不更新 git config**、不跳过 hooks、不用 `-i` 交互、不 force-push，除非用户明确要求
* **commit 失败**（如 hooks 拒绝）：修复问题后创建**新提交**，不 `--amend` 失败的提交
* **空提交**：不创建无改动的提交，除非用户明确要求
