# Git 提交消息规范

## 格式

```
<类型>(<范围>): <描述>

<正文：空一行后书写，按模块/动机分条说明>

<脚注：可选>
```

## 类型

| 类型 | 用途 |
| ------ | ------ |
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `docs` | 文档更新 |
| `style` | 代码格式（不影响功能） |
| `refactor` | 重构（既不修复 bug 也不添加功能） |
| `test` | 添加或修改测试 |
| `chore` | 构建过程、辅助工具、依赖变更 |
| `perf` | 性能优化 |
| `ci` | CI 配置变更 |
| `build` | 构建系统或外部依赖变更（Cargo.toml、package.json） |
| `revert` | 回滚之前的提交 |

取**主要变更**的类型。一次改动里 refactor 为主、附带小 fix，则用 `refactor`。

## 范围（可选）

受影响的模块或子系统，用小写短词，对应 crate 名、包名或模块名（如 `cli`、`api`、`config`、`parser`、`auth`）：

* 单模块内：写该模块名
* 跨模块 / 跨包：**省略范围**，或用概括词（如跨多个工具用 `tools`）

判断标准：读者看范围就能预判 diff 涉及哪里。拿不准就省略。

## 标题规则

1. **中文**撰写（标题与正文均使用中文）
2. **命令式语气**：说"迁移配置"而非"迁移了配置"；"移除字段"而非"移除了字段"
3. **不超过 72 字符**（中文按字数，含类型与范围前缀）
4. **句末不加标点**（无句号、无冒号收尾）
5. 类型 + 范围前缀与描述之间用 `:` 分隔
6. 标题已能完整表达时，正文可省略

## 正文规范（可选）

标题之外需补充**为什么**改、**改了什么**时写正文：

1. 标题与正文之间**空一行**
2. 每行不超过 72 字符，超长折行
3. 按**动机 → 内容**组织：先讲为什么改（背景/问题），再列具体改了什么
4. 多模块改动用分条（`-` 或换行）按模块/主题列出
5. 解释 **Why**（为什么这样改），而不是重复 **What**（diff 已经能看出 What）

## 跨模块改动的消息写法

一次变更跨多个模块时，用**一条消息**概括整体：标题写整体变更方向（类型取主要变更类型，范围跨模块时省略或用概括词），正文按模块 / 主题分条列出。
