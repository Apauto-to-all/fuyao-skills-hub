## P3 入库来源：skills.sh 寻址

**现状**：`fsh add <dir>` 只吃本地目录，`--prefix` 只管键的组织前缀、与来源无关。装一个上游技能得先自己 clone 到本地，多一步，还要求机器上有 git——而 fsh 的立场是不依赖用户装 git，`git2` 已静态链进 exe，克隆能力本来就在。

**想法**：入参先按 skills.sh 的寻址形状适配——`owner/repo` 简写、完整仓库 URL、仓库内子目录 URL（`…/tree/<分支>/skills/<名>`）、任意 git URL；本地路径保持现状。一个仓库常有多个技能：先 `--list` 看清单，再 `--skill <名>` 选（`*` 全要）。来源只决定「从哪拿」，键仍由 frontmatter 的 name 末段加 `--prefix` 决定。

**开工先定**：

1. 临时克隆与清理：浅克隆到 hub 外的临时目录（`git2` 已有网络能力），失败要把临时目录整份删干净，不留半个工作副本
2. 多个 `SKILL.md` 的选取：`--skill` 按 `name` 匹配；重名或未命中要回可用清单，不能只报「找不到」
3. 默认前缀：从 URL 自动补组织名当键前缀（`owner/repo`）看着顺，但会把「名字唯一来源 frontmatter」这条规则撕开一道口；倾向前者不做，前缀仍旧只由 `--prefix` 给
4. 凭据边界：公开仓库之外先报 `auth_not_supported`，私库凭据留给 P4 的凭据体系，不在 `add` 里各造一套
5. zip 来源：没有网络与凭据问题、解压即用，但和 git 来源是两条路，先不做
6. `--list` / `--skill` 不能只长在 URL 分支：本地目录同样适用，否则两条入参各半套能力
7. 许可与体积：入库前要不要拦超大仓库或没有许可声明的仓库，先只记事实、不设闸

## P4 Git 远端同步（M3）

**现状**：没有 `fsh sync`，core 里也没有任何远端逻辑；`git2` 已静态链进 exe，网络能力本来就在。单副本空窗（换机器、重装）眼下没有兜底。

**验收标准**：两台机器同步同一个 hub，内容一致。

**想法**：未成形——只有上面这一条验收标准。底子已定：单仓、main 单分支、无 tag、写命令自动提交，纯 fast-forward 即可同步。

**开工先定**（尚未讨论）：

1. 同一个键在两台机器都动过的冲突策略：拒绝并要求人工合并，还是按时间取新
2. GitHub 私有库的凭据存在哪：不进 hub 的 git，也不平铺在 `hub.toml`
3. `push` 与 `pull` 是一个命令（`fsh sync --push|--pull`）还是两个命令

## P6 doctor 修复

**现状**：`fsh doctor` 只报不动（吸收了原 gc 的全部检查项：登记簿死记录、孤儿落点、孤儿目录），FAIL 时退出码 1；发现的问题要人工按报告逐条处理。

**想法**：给 doctor 加 `--fix`，把报告里能安全自动修复的项一键处理（清死记录、删孤儿落点/目录）；不能安全自动修的仍然只报。

**开工先定**：

1. 哪些项算「能安全自动修」：死记录与孤儿目录无歧义，脏 copy 落点（内容被改过）要不要动
2. `--fix` 是全修还是按项选择（`--fix records` / `--fix orphans`）
3. 修复后的自动提交：一次一条还是每次 fix 合并一条

## P7 GitHub 开源 + npm 发布

**现状**：安装只有 `cargo install --path crates/fsh-cli` 一条路，要求用户装 Rust。exe 已是单文件无依赖（release 实测 5.43 MB：`git2` 静态链接、伴生技能内嵌、hub 数据与程序解耦），「安装」本质就是拷进 PATH。仓库未开源，npm 账户没有。代码 Windows 专属：`junction` 依赖与三处 `#[cfg(windows)]`（`link.rs` 链接引擎、`logging.rs`），非 Windows 编译不过。

**想法**：两件事绑一件做——GitHub 开源仓库，npm 按「wrapper 主包 + 平台二进制包」模式发布（esbuild/biome 同款）：主包纯 JS 按 `process.platform/arch` 从 optionalDependencies 里选平台包、找到 exe 转发参数与退出码，用户 `npm i -g fsh` 免 Rust。发布前可本地零账户演练：`npm pack` / `npm publish --dry-run` 验包内容，`npm link` 验 bin 转发，verdaccio 本地 registry 走完整发布→安装闭环。

**开工先定**：

1. 顺序与绑定：公开 registry 的包任何人可下载二进制——先 npm 后开源是否成立，还是开源是发布前置；若坚持闭源发 npm 只能走付费私有包或 GitHub Packages
2. 平台矩阵：首版只发 win32-x64、其余平台装主包时报清晰错误，还是先补一张跨平台票再发；npm 包名查重（`fsh` 裸名是否被占）与 `@scope` 命名，连同 GitHub repo 名一次定
3. CI 与发布触发：GitHub Actions windows runner 出 exe，cargo-dist 一条龙（Release + npm 包同源生成）还是手写 workflow；tag 触发还是手动
4. 版本单一来源：Cargo `0.1.0` 与 npm 版本谁跟谁走，发版前要不要 CHANGELOG
5. 许可与开源范围：workspace 已定 Apache-2.0，npm 包 license 字段对齐；GUI（`src/`、`src-tauri/`）与文档是否同仓同行，还是只开 CLI 相关
6. 账户准备：npm 账户 + 2FA（发布强制）、granular access token、GitHub 侧 org/仓库可见性
