# fuyao-skills-hub 未来计划

> 本文件只收**还没实现**的想法；`设计文档.md` 只写已交付的功能，界线是「代码里有没有」。动工走流程 A，`/grill-with-docs` 先把「开工先定」逐题问完；规格建成后本条整段删除，不留指针。

## P3 入库来源：skills.sh 寻址

**现状**：`fsh add <dir>` 只吃本地目录，`--prefix` 只管键的组织前缀、与来源无关。装一个上游技能得先自己 clone 到本地，多一步，还要求机器上有 git——而 fsh 的立场是不依赖用户装 git，`git2` 已静态链进 exe，克隆能力本来就在。

**想法**：入参先按 skills.sh 的寻址形状适配——`owner/repo` 简写、完整仓库 URL、仓库内子目录 URL（`…/tree/<分支>/skills/<名>`）、任意 git URL；本地路径保持现状。一个仓库常有多个技能：先 `--list` 看清单，再 `--skill <名>` 选（`*` 全要）。来源只决定「从哪拿」，键仍由 frontmatter 的 name 末段加 `--prefix` 决定。

**开工先定**：

1. 临时克隆与清理：浅克隆到 hub 外的临时目录（`git2` 已有网络能力），失败要把临时目录整份删干净，不留半个工作副本
2. 多个 `SKILL.md` 的选取：`--skill` 按 `name` 匹配；重名或未命中要回可用清单，不能只报「找不到」
3. 默认前缀：从 URL 自动补组织名当键前缀（`owner/repo`）看着顺，但会把「名字唯一来源 frontmatter」这条规则撕开一道口；倾向前者不做，前缀仍旧只由 `--prefix` 给
4. 凭据边界：公开仓库之外先报 `auth_not_supported`，私库凭据留给 P4 的凭据体系，不在 `add` 里各造一套
5. zip 来源：没有网络与凭据问题、解压即用，但和 git 来源是两条路，先不做
6. `--list` / `--skill` 不能只长在 URL 分支：本地目录同样适用，否则两条入参各半套能力
7. 许可与体积：入库前要不要拦超大仓库或没有许可声明的仓库，先只记事实、不设闸

## P4 Git 远端同步（M3）

**现状**：没有 `fsh sync`，core 里也没有任何远端逻辑；`git2` 已静态链进 exe，网络能力本来就在。单副本空窗（换机器、重装）眼下没有兜底。

**验收标准**：两台机器同步同一个 hub，内容一致。

**想法**：未成形——只有上面这一条验收标准。底子已定：单仓、main 单分支、无 tag、写命令自动提交，纯 fast-forward 即可同步。

**开工先定**（尚未讨论）：

1. 同一个键在两台机器都动过的冲突策略：拒绝并要求人工合并，还是按时间取新
2. GitHub 私有库的凭据存在哪：不进 hub 的 git，也不平铺在 `hub.toml`
3. `push` 与 `pull` 是一个命令（`fsh sync --push|--pull`）还是两个命令

## P6 doctor 修复

**现状**：`fsh doctor` 只报不动（吸收了原 gc 的全部检查项：登记簿死记录、孤儿落点、孤儿目录），FAIL 时退出码 1；发现的问题要人工按报告逐条处理。

**想法**：给 doctor 加 `--fix`，把报告里能安全自动修复的项一键处理（清死记录、删孤儿落点/目录）；不能安全自动修的仍然只报。

**开工先定**：

1. 哪些项算「能安全自动修」：死记录与孤儿目录无歧义，脏 copy 落点（内容被改过）要不要动
2. `--fix` 是全修还是按项选择（`--fix records` / `--fix orphans`）
3. 修复后的自动提交：一次一条还是每次 fix 合并一条

## P7 GitHub 开源 + npm 发布

**现状**：安装只有 `cargo install --path crates/fsh-cli` 一条路，要求用户装 Rust。exe 已是单文件无依赖（release 实测 5.43 MB：`git2` 静态链接、伴生技能内嵌、hub 数据与程序解耦），「安装」本质就是拷进 PATH。仓库未开源；npm 账户已注册（终端 `npm login` 尚未授权），GitHub 侧 org 与仓库已就位、待转 public。代码 Windows 专属：`junction` 依赖与三处 `#[cfg(windows)]`（`link.rs` 链接引擎、`logging.rs`），非 Windows 编译不过。npm 查重已完成：裸名 `fsh` 被 2011 年的僵尸包占用，`fuyao-skills-hub` 未被占。更新检查不在本条（见 P8）。

**想法**（命名与发布方案已定）：GitHub 开源先行，npm 后发。包名 `fuyao-skills-hub` 裸包（与仓库名一字对齐），bin 命令 `fsh`，安装即 `npm i -g fuyao-skills-hub`。v1 发单包、不拆平台包：`os: ["win32"]` + `cpu: ["x64"]` 让非 Windows 安装直接收到 npm 原生 `EBADPLATFORM` 错误，包内放 exe 加一个 JS bin shim 转发参数与退出码，将来支持其他平台再拆平台子包。CI 用手写 tag 触发 workflow（GitHub Actions windows runner 构建 exe、Cargo.toml 版本同步进 package.json 后发布），不用 cargo-dist。发布认证走 trusted publishing（OIDC，不存长生命周期 token——该类 token 2027-01 起禁止直接 publish；注意 trusted publishing 配置创建后 2 天内必须完成首次成功发布，否则过期作废）。版本单一来源是 workspace `Cargo.toml`；license 按既定 Apache-2.0 对齐 npm 字段；首版不做 CHANGELOG。发版顺序：包工程与 bin shim 进仓 → verdaccio 本地 registry 演练发布→安装闭环（`npm pack` / `--dry-run` 验包内容，`npm link` 验 bin 转发）→ 仓库转 public → 终端 `npm login` 手动发 v0.1.0 → npmjs.com 包设置页配置 trusted publishing → 合入 workflow → 后续版本打 tag 全自动发布，并按官方建议把包设置收紧为「Require 2FA and disallow tokens」。

**开工先定**：

1. 开源范围：整仓开源（GUI 已冻结但同仓同行）还是只开 CLI 相关目录与文档
2. npm 包工程落点：根 `package.json` 属 GUI（`fsh-gui`），发布包工程新开目录的位置与结构
3. README 对外门面：现状未盘点，发布前要过一遍安装、用法、license 与仓库链接

## P8 更新检查（0.1.1）

**现状**：npm 包未发布（P7 未实施），core 无任何版本检查逻辑；`fsh --version` 由 clap 原生输出。registry 上没有可比对的目标版本，更新检查只能在 0.1.0 发布之后的 0.1.1 落地。

**想法**（形态已定）：任意 `fsh` 子命令运行时被动检查，状态文件存 hub 内并 24 小时节流；查询走 `npm view fuyao-skills-hub version`（npm 分发保证装了 fsh 就有 npm，零新增 HTTP 依赖）；发现新版在 stderr 追加一行 agent 友好提示（含可复制的 `npm i -g fuyao-skills-hub@latest`），命令输出与退出码不受影响；`fsh doctor` 加版本检查项（当前 vs latest，离线记 SKIP 不算 FAIL）；网络失败静默跳过。不做专门检查命令（没人记得敲），不做自替换升级（Windows 运行中 exe 锁定，且 npm 装的包由 npm 管）。

**开工先定**：

1. 状态文件形状与落点：hub 内路径、字段（上次检查时间、latest 版本），须对齐 .gitignore 白名单机制不进版本库
2. 版本比较：引入 semver crate 还是手写三元组比较（字符串比较会错判 0.10.0 < 0.9.0）
3. doctor 项的判定级别：版本过时算 WARN 还是 FAIL（现状 FAIL 才退出码 1）
4. 提示覆盖面：所有子命令都提示，还是排除 doctor / --version 自身避免重复
