# fuyao-skills-hub 设计文档

> 本文档是个人版功能全集：要实现什么、已经有什么、还缺什么。
> 状态标注：✅ 已实现（fsh-core / fsh-cli，测试全绿）· 🟡 部分实现 · ⬜ 未实现

---

## 0. 一页摘要

一个本地优先的 skills 管理工具：一个中心库（hub）存所有 skill，按项目把需要的 skill 以链接方式铺进各 agent 认的技能目录（通用位 `.agents\skills\`，或 agent 自己的目录）。可视化界面（给人）+ CLI（给 AI 调），带 Git 同步。

**技术栈**：Rust workspace——`fsh-core` / `fsh-cli` 两 crate + Tauri 2 GUI（`src-tauri`，crate 名 `fsh-gui`）；crate 数量冻结，禁止新增；TS 只出现在 webview 前端。CLI 与 GUI 均单 exe。

**hub 布局**：数据住家目录点目录 `~\.fuyao-skills-hub`，与程序解耦；定位链 `--hub` > `FSH_HUB` > 缺省。

---

## 1. 需求清单（验收以此为准）

1. 个人自用为主
2. GUI（人）+ CLI（AI）双入口，两边都能改，状态一致
3. 项目级固定 skill 集，手动或 AI 定（不要运行时动态揭露）；一个技能可按需铺给多个 agent，各 agent 从自己的目录读
4. Git 同步 / 升级，GitHub 起步
5. 可视化

## 2. 架构

### 2.1 分层与 workspace（定稿）

```
fuyao-skills-hub/            # Cargo workspace
├─ crates/fsh-core/          # 纯逻辑：git、paths、hub、link、lock、gc、doctor、skill
│  ├─ src/agents/            # 规划中：内置 agent 名单（代码常量）+ 读取用户 TOML 覆盖
│  └─ src/git/               # ✅ git2（libgit2）封装——静态链接进 exe，不依赖用户装 git
├─ crates/fsh-cli/           # ✅ clap → fsh 命令；全命令 --json，写操作 --dry-run
├─ src-tauri/                # 🟡 Tauri 2 薄桥（fsh-gui）：command 只调 fsh-core，不含业务逻辑
└─ src/                      # 🟡 React 19 + TS —— 全项目唯一 TS 存在处
```

**模块数量冻结**：`crates/` 下只有 `fsh-core` 与 `fsh-cli`，禁止新增任何 crate；一切后续职责（agent 配置、检索等）一律作为 `fsh-core` 内部模块落地。

**铁律**：代码里没有 agent 专属分支——agent 只是数据（内置名单 + 用户 TOML 覆盖）；UI 不进业务逻辑。业务逻辑 100% Rust。

### 2.2 hub 目录布局（家目录点目录，定稿）

```
~\.fuyao-skills-hub\                # hub 根 = 一个 git 仓库（缺省位置）
├─ .git\                            # 真身：版本历史、tag、diff、审计全在这
├─ .gitignore                       # 白名单：只放行 .gitignore / hub.toml / agents\ / store\
├─ .lock                            # 进程级文件锁：hub 全局写互斥（ignored）
├─ hub.toml                         # tracked：user 身份、gc 配置
├─ agents\<名>.toml                  # tracked：覆盖或新增 agent 配置（内置表在代码里，形状见 2.6）
├─ store\
│  └─ <键>\                          # tracked 工作副本（可脏；元数据唯一住所在 SKILL.md frontmatter）
│     └─ SKILL.md  references\
├─ projects.toml                    # ignored 登记簿：用法的唯一记录（形状见 2.3）
├─ export\                          # ignored 导出目录根
│  └─ <键>\<版本>\                   # 导出目录（固定版本用）
└─ logs\                            # ignored 日志（按天滚动，保留 30 天）
```

- hub 定位链只有一条：`--hub` 显式根 > 环境变量 `FSH_HUB` > 缺省 `~\.fuyao-skills-hub`（家目录由标准库 `std::env::home_dir()` 解析）；空字符串环境变量视为未设置；家目录解析失败为硬错误，报错提示设置 `FSH_HUB` 或 `--hub`。
- 仓库本地 `core.autocrlf=false`。
- 卸载 = 删 exe + 删 `~\.fuyao-skills-hub`；安装 / 更新只动 exe，数据永不参与。

### 2.3 项目侧布局（⬜ 重设计）

项目里不放 fsh 的任何文件。fsh 只往各 agent 认的技能目录里铺技能（链接，降级时是拷贝），用法的唯一记录在 hub 的 `projects.toml`。

```
<project>\
├─ .agents\skills\<name>\             # 通用位（skills_dir = ".agents/skills"）
└─ <该 agent 的 skills_dir>\<name>\   # 按 agent 配置里的 skills_dir 落点
```

记录的形状（hub 的 `projects.toml`，ignored，「作用域 → 身份 → 记录」三层）：

```toml
[projects."E:\\proj\\demo"]           # 表键 = 项目身份，规范化绝对路径
last_used = 1762301234                # 最后一次被 fsh 操作的时间

[[projects."E:\\proj\\demo".skills]]
key = "manage-skills"                 # hub 里的唯一键；键末段就是 name，不另存
version = "0.1.0"                     # 可选：不写 = 跟最新
agents = ["universal", "opencode"]    # 给哪些 agent 用；通用位取值 universal
link = "symlink"                      # 实际采用的方式：symlink | junction | copy；一条记录一个值，作用于 agents 列出的所有 agent
```

- 项目身份就是表键，于是每条技能块的 header 自带归属，同一项目的技能永远相邻
- 表键取规范化绝对路径原样（Windows 下带 `\\?\` 前缀）：剥掉前缀的超长路径做不了文件操作

- 落点不落记录，由 agent + 键末段现算（见 2.6 的 agent 配置）
- 一个技能给多个 agent 就是 agents 列表里多个值，不拆多条记录
- 名字必须等于目录名：各 agent 都按目录名校验技能，所以记录里只存 key
- `use` 只对存在且未归档的 skill 执行；登记簿没有这条记录、且全部落点不存在，任一不成立就报错停下，磁盘一个字不动
- 多个 agent 解析到同一落点时只建立一次入口，登记仍保留全部 agent；同一次使用的全部落点必须采用同一种链接方式，不能统一则失败并回滚
- 项目目录必须已存在，规范化为绝对路径后作为登记簿身份；技能父目录可由 fsh 创建

### 2.4 版本模型：git 为真身，按需导出（定稿 ✅）

版本的唯一实体是 git tag（`<键>/v<semver>`）；`export\<键>\<版本>\` 只是 tag 的按需导出（导出目录），可随时删、按字节重建。

- **版本号只能往前走**：文件里写的号不大于已发布的最新版本时，提示并停下，由 AI 或用户改号后重跑
- **链接靶子**：默认项目跟最新，链接直指工作副本，改完就是最新；只有固定具体版本的项目才链到导出目录
- 入库与发布版本都只产生 commit 与 tag，不复制目录、不生成导出目录
- 升级 / 回滚 = 先 unuse，再 use 指定版本（记录还在时 use 会拒绝）
- 固定版本复用已有导出目录前按 tag 校验内容；一致才复用，不一致则报错并保留现场，绝不自动覆盖
- git log 是原始审计账本

### 2.5 GC：及时、定向、无损（🟡 部分实现）

| 对象 | 策略 |
|---|---|
| 无记录引用的导出目录 | 清（grace_days 宽限内保留） |
| 孤儿目录（无对应 tag） | 清 |
| 内容与 tag 不符的脏目录 | 跳过并报警（可能是手改证据，绝不销毁） |
| git tag / 历史 | 永不清 |
| 登记簿死项目记录 | 清（grace_days 宽限）：判定 = 登记簿里的项目路径已不存在 |

三层执行，零后台进程：① **顺手清**：use 成功后当场查引用；② **`fsh gc [--dry-run]`**：全量，先列清单再执行；③ **doctor 只报不动手**。引用查找只读登记簿（毫秒级）；只有 gc 清死记录时才 stat 登记簿里的项目路径。黑链接 = 指向 hub 但不在登记簿里的链接，排查留给 `doctor --scan`。

### 2.6 链接引擎与 agent 配置（Windows，✅ / ⬜）

三级降级，必须实现：目录符号链接 → junction → 拷贝，实际用了哪种记在 projects.toml 的 link 字段。已知坑：云盘路径破坏 reparse point（doctor 检测）；拷贝不跟源同步，改完不回流，链路断了只能重铺。

agent 配置（✅，数据不是功能）：内置表写死在代码里，随 fsh 发布版本更新，名单与 `vercel-labs/skills` 的 `src/agents.ts` 同步；用户在 hub 根 `agents\<agent名>.toml` 放同名文件即可覆盖内置项，放新文件名即新增一个 agent。

```toml
display_name = "DeepSeek Harness"   # 可选：给人看的名字，缺省显示文件名
skills_dir = ".dsh/skills"          # 可选：项目落点，相对项目根
global_skills_dir = "~/.dsh/skills" # 可选：全局落点，可移植写法
```

- 键就是文件名：`use --agent dsh` 先找 hub 根 `agents\dsh.toml`，没有就用内置项
- 用户 TOML 与内置项同名时整项覆盖，不做字段级合并；文件存在但非法即报错，不回退内置项
- 内置名单只抽取上游名称、显示名、项目相对技能目录与全局技能目录，另补自有 `dsh`；通用位沿用上游 `universal` 但全局位取 `~/.agents/skills`，随 fsh 发布静态更新，不联网同步
- 落点 = `skills_dir\<技能名>`（项目）或 `global_skills_dir\<技能名>`（全局）；技能名取键末段（键可多级，如 `mattpocock/skills/tdd` → `tdd`）
- `skills_dir` 必须是相对路径，不许绝对路径、不许 `..`
- `global_skills_dir` 只为 fsh 建模：落点永远先展开成绝对路径再建链接，agent 工具只会看到绝对路径
- 两个目录至少给一个：只给项目目录的 agent 只能项目使用，只给全局目录的 agent 只能全局使用（`agent_no_project_dir` / `agent_no_global_dir` 分别点名）
- 全局目录三类写法：`~` 前缀（只认开头的裸 `~`，不认 `~user`）、环境变量（`%NAME%` 与 `$NAME` / `${NAME}`，未设置即报错，绝不静默留成字面量）、绝对路径；展开结果必须是绝对路径，禁止 `..` 与空串
- 绝对路径写法只在这台机器成立：`agents\*.toml` 是 tracked，写死绝对路径会绑死机器，跨机配置只用前两类
- 非法写法一律报 `invalid_agent_config`，错误里点名 agent 与字段
- 未知字段报错，不静默忽略
- `use --agent xxx` 两处都找不到 → 报错并列出认得的 agent
- 通用位不是特例：`universal` 就是 `skills_dir = ".agents/skills"` 的普通一项
- 全局落点与全局使用 / 撤回均已落地（见 §7.1）

### 2.7 数据与程序解耦立场

数据住 `~\.fuyao-skills-hub`，与程序生命周期解耦（产品立场，写进 README）：安装 / 更新只动 exe，数据永不参与；卸载 = 删 exe + 删数据目录。doctor 运行时安全检测（hub 根可写 / 非云盘）✅；exe 占用更新协议（旧 exe 改名 → 放新 → 启动删旧，见 §8.7）⬜。单副本空窗由 M3 的远端同步兜底。

## 3. CLI 设计（✅ 已接线：库管理、项目使用与全局使用）

**设计原则**：命令必须精简高效，每条要证明自己不可替代，证明不了就合并或删除；命令面逐条经用户拍板，不预设全集。

给 AI 用是第一优先级：**所有命令支持 `--json`，所有写操作支持 `--dry-run`**。

命令里的 `<skill>` 一律是**唯一键**（`store\` 内相对路径），不是 frontmatter 里的 name：多级键必须写全（`mattpocock/skills/tdd`），不提供按末段或按 name 的模糊匹配，查不到即报 `skill_not_found`；`<skill>@<版本>` 的 `@` 前同样是完整键。键与 name 的关系见术语表「唯一键」。

```bash
fsh init [--hub <dir>]                      # ✅ 幂等初始化：建 store/ export/ agents/ 三个空目录 + .gitignore + hub.toml；装配残缺时补齐缺件；--hub 指 hub 根，缺省 ~/.fuyao-skills-hub（接远端归 M3）
fsh add <dir>                               # ✅ 入库：名字唯一来源 frontmatter（无 --as）；git-url/zip 推后续里程碑
fsh list [--tag]                            # ✅ 薄行含最新版本、归档态、来源
fsh search <pattern> [路径...] [rg 参数]     # ⬜ 内置 ripgrep 引擎：找到技能与搜到内容（见 3.1）
fsh show <skill>                            # ✅ frontmatter 全字段 + 版本时间线 + 被引用项目与全局装着它的 agent
fsh release <skill>                          # ✅ 发布版本：按 frontmatter 里写的号（号由文件定），未提交的改动一并提交，再打 tag
fsh archive <skill>                         # ✅ 归档：先查登记簿，被项目或全局用法引用即拒绝；通过后删工作副本与导出目录，tag 与历史全留，可 restore
fsh remove <skill>                          # ✅ 彻底删除：连全部 tag 删，被项目或全局用法引用即拒绝，无 --force
fsh restore <skill>                         # ✅ 从最新 tag 复活工作副本，不打新 tag（回旧版本不走这条——unuse 后用 @版本 重铺）
fsh use <skill>[@<version>] --agent <a>[,<b>] (--global | --project <目录>…) [--dry-run]  # ✅ 一次服务多个目标：可选一个全局目标 + 零到多个项目目标；全部目标一起预检，任一不合格整次不动盘；失败回滚，成功各写一条登记记录并顺手 GC
fsh unuse <skill> [--agent <a>[,<b>]] (--global | --project <目录>…) [--force] [--dry-run]  # ✅ 撤回同样按目标集合：给 --agent 只撤这些 agent，不给则整体撤回；三种组合各撤净对应落点与登记，未涉及目标一字不动；先检查全部落点，再删落点与登记
fsh agents                                  # ✅ 列出认得的 agent：名字、显示名、目录、内置或用户覆盖来源
fsh gc     [--dry-run]                      # ✅
fsh diff   <skill> <v1> <v2>                # ✅ unified diff 按文件
fsh doctor                                 # ✅ 七项：hub 根可写 / 云盘路径 / 链接能力 / hub 装配与可读性 / 导出目录缺失 / 登记簿不可达（项目路径不存在或登记簿读不出） / 可回收空间；FAIL 时退出码 1（--scan 未实现）
fsh sync [--push|--pull]                    # ⬜ 与远端 Git 同步（M3）
```

撤回的完整语义：

- `unuse` 按目标集合撤回：可选一个全局目标 + 零到多个项目目标，三种组合（只全局 / 只项目 / 两者并存）都一次撤净对应落点与登记记录，未涉及的目标一字不动；没有目标时报 `no_target`
- 给 `--agent` 时按 agent 撤回：只撤名单里那些 agent 的落点并从记录里摘掉它们，共用落点留到最后一个引用它的 agent 也被撤走时才删；名单里出现记录没有的 agent 报 `agent_not_registered`
- 不给 `--agent` 时整体撤回：撤该目标下此技能的全部 agent 落点，删整条登记记录
- 执行前先检查全部落点，任一目标不合格则整个操作不动盘；要留下的 agent 解析不出同样报错不动盘
- copy 与当前 `use` 源目录逐文件比较；不一致即视为修改并拒绝撤回，源目录后续变化造成的保守误报也由 `--force` 显式确认
- `--force` 只覆盖“登记为 copy 且内容被修改”的安全闸；链接类型与登记不符时始终拒绝，由用户手工处理
- 落点已缺失视为已撤回；登记簿无该技能记录则报错，不扫描或删除黑链接
- 撤回成功后：整条撤净或名单点满记录时删除整条技能记录，只撤一部分时记录里只摘掉那些 agent；项目无其他技能时删除项目记录，全局段无其他技能时整段略去

被引用判定（`archive` / `remove` 共用）：项目段与全局段一起看，任一非空即拒绝；报错同时给出引用项目路径与占用它的全局 agent。

配套一个 `manage-skills` 伴生 skill：告诉 Agent 什么时候调哪个命令、`--json` 怎么读、禁止直接改 hub 文件。**这是「AI 自己管理」的落地点。**

### 3.1 检索（⬜ 待实现）

`fsh search` 把 ripgrep 的检索能力装进进程：依赖 `ignore` 与 `grep` crate（ripgrep 本体），不起外部 `rg.exe`，单 exe 不变。

- **参数面先与 rg 对齐**：不预先裁剪，实测不好用的再删；fsh 只补下面四样
- **作用域固定**：根恒为 hub 根；位置路径相对 hub 根，`..` 与越界一律拒绝
- **归档不进检索**：归档技能没有工作副本，遍历天然看不到，不需要写排除逻辑
- **与 rg 的差异只有三处**：作用域固定；`--json` 走项目信封 `{"ok":true,"data":…}`（rg 是逐事件 JSON 流）；无命中退出码 0（rg 是 1）
- **fsh 附加**：`--skills`（key + 描述 + 标签）、`--tags`（每个 tag 与计数）、`--tag`（多值 AND）、`--limit`（默认 200，超出标 `truncated`）
- 输出：文本模式 `path:line:text`；JSON 每条命中带 `key`
- GUI 库页左栏复用同一份能力，不另写筛选逻辑
- 技能枚举与现有 `fsh list` 的重合处在规格阶段一并收敛

## 4. GUI 设计（🟡 四页已落地）

四页，不多做：

1. **库（Library）**：卡片/表格，按 tag、来源筛；详情 + SKILL.md 预览
2. **版本（Versions）**：时间线、两版 diff、一键回滚、谁在用这个版本
3. **项目（Projects）**：登记簿记录表、一键 use / unuse
4. **Agent**：每个 agent 的名字、目录、当前链了哪些 skill

可视化只做三张图：使用与版本分布 / 项目 × skill 覆盖矩阵 / 引用图。

## 5. 索引层（已舍弃）

SQLite 索引不再实现。库的规模是一个人维护的几百个技能：「有哪些技能」是一次目录遍历（不碰 git），「找技能 / 搜内容」由 §3.1 的 ripgrep 引擎即时完成，两者都不需要预先建索引。反过来，索引要为「git 仓库随时被 CLI、手改、checkout 改动」维护缓存失效，成本高于收益。

真出现可测的慢（`fsh list` 或进库页超过 200ms）时，先做的是把逐键的 tag 遍历合并成一次扫描，仍不动索引。

### 8.3 伴生技能内置与全局自举

现状：伴生技能住在仓库 `skills\manage-skills\`，名字 `manage-skills`，得手工 `fsh add` 才进 hub，再逐个 agent `use` 才铺出去。它讲的是 fsh 自己的用法，属于程序的一部分，不是用户内容。

已拍板的决定：

1. **改名 `fuyao-skills-hub`**：技能名、唯一键、落点目录名都用它，不再用 `manage-skills`；键上不加前缀。
2. **内置，不进 hub 的 git**：随程序发布，不放进 `store\`，不参与 tag / 发版 / 归档 / 回收；`list` 与 `show` 要能看见它，并标成内置。
3. **`use` 与 `unuse` 都能处理内置技能**：铺与撤走与普通技能同一套目标集合、落点、回滚与登记语义；只有技能本体不可 `release` / `archive` / `remove`（它是程序资产，不是 hub 内容）。
4. **同名覆盖**：内置与用户技能共用同一键空间，不设保留前缀。`store\` 里有该键时以 store 为准，内置被整项覆盖（与 agent 配置「同名文件整项覆盖内置项、不做字段级合并」同一约定）；`store\` 没有该键时才用内置。

为什么不做保留前缀：用户真去建一个同名技能时，前缀会让两份技能抢同一个落点目录名，冲突只能靠报错挡回去；共键空间 + store 优先让「同名」变成自然覆盖，`add` 也不必再维护一份保留前缀黑名单——你反过来说的「不支持反而不好实现」成立，前缀方案要多写一条拒绝规则，还留着落点冲突。

内置的固定词是 `builtin`：磁盘实体目录 `builtin\<键>\`、`list` / `show` 的来源标记、相关错误码与报错文案都用这个词；键本身不带前缀。

动工前必须解决：

1. 遮蔽后的可见性：`store\` 有同名键时 `list` / `show` 只呈现用户那份；是否在 `show` 里提示「内置版本已被同名技能覆盖」待拍板。
2. 只读边界：`release` / `archive` / `remove` 只对 `store\` 那份生效；`store\` 无该键时对内置执行要报错，文案说清「先入库自己的同名技能再改」。
3. 登记错位：先 `use` 内置、之后 `add` 同名技能，已登记用法仍指向内置内容，而 `show` 已显示用户那份。拟在 `add` 时检测该键已有用法即拒绝并提示先 `unuse`（待拍板）。
4. 升级刷新：程序升级后内置实体整份覆盖；symlink / junction 落点自动跟随，copy 落点要重铺（或由 `doctor` 报出、用户手动 `unuse` 后重铺）。
5. 源目录：链接总要指向一个真实目录——内置技能在 hub 根下 `builtin\<键>\`（ignored）落一份实体，链接指向它；copy 模式下用户改动不回流。
6. 排除：`gc` / `projects` 视图里内置技能的位置写死，避免被当普通入库技能处理。
7. 自举入口：`--agent` 加 `all`（展开成内置表里所有有全局位的 agent），还是单独的便捷命令；倾向前者，不新增命令面。
8. 版本：内置内容跟程序版本走，登记记录的 `version` 留空（= 跟最新），`list` / `show` 显示「内置 · v<程序版本>」。
9. 键的写法：与 §8.5 一致，多级键一律 `/` 分段。

> 状态：⬜ 未实现，排期未定（与「frontmatter 字段合理化」一起考虑，内置技能的形状要按新字段规范定稿）。

### 8.4 frontmatter 字段合理化

现状：fsh 只认 SKILL.md 顶部 frontmatter 的五个平铺字段 `name` / `description` / `version` / `source` / `tags`，其余字段不解析、随内容透传。其中 `version` 是 fsh 自造的发版输入（版本真身是 git tag），`source` / `tags` 也是 fsh 自造的平铺字段。

想法：尽量只占用各 agent 工具官方支持的字段，fsh 自己的字段收进有命名空间的位置（官方扩展位，或 `metadata:` 下的 fsh 子键），不平铺在顶层。风险动机：平铺自造字段会与官方 schema 的保留字段撞名，或随官方演进被改成不同含义；不同工具对未知顶层字段的容忍度也不一样，被拒解析时技能直接不可用。

- `name` / `description`：官方字段，保持现状；`name` 必须等于目录名（键末段）这条规则也保留。
- `version`：官方没有这个概念，收进命名空间；或者干脆取消文件内写号、改成 `fsh release <skill> <版本>` 显式给号——后者推翻「号由文件定、写者是 AI」的现有设计，需要单独拍板。
- `source` / `tags`：官方有等价字段就复用，没有就进命名空间。
- 零兼容：形状一旦变，旧 store 里的技能现场手改一次，不写双形状识别、不做迁移。错误要把缺字段或错位置点名到文件与字段。

前置改动：

1. 先做对照表：各 agent 工具的 SKILL.md 官方字段全集 + 允许的扩展位，确认哪些能复用、哪些必须进命名空间。
2. `manifest` 解析、`list` / `show` 回显、GUI 表单、伴生技能模板随之改形状。
3. 与 §8.3 的先后：内置技能的内容按新字段规范定稿，避免刚改完名又改一遍字段。

> 状态：⬜ 未实现，排期未定。

### 8.5 键的斜杠统一与入参校验

现状：唯一键已经是「`store\` 内相对路径、用 `/` 分段」的形态——`naming.rs` 是全库唯一的拼装点，版本 tag（`<键>/v<版本>`）、`store` 子路径、导出目录三族名字都用 `/`；`walk_store` 也拼 `/`；`add` 的 `--prefix` 明确拒绝反斜杠、空段、`.` / `..`、盘符与版本形状的段，报错文案写的就是「正斜杠路径」。

不统一的只在入参：`use` / `unuse` / `show` / `diff` / `release` / `archive` / `remove` / `restore` 收的 `<skill>` 是原样字符串，`\` 既不归一也不校验。于是 `use mattpocock\skills\tdd ...` 会拼出 `store/mattpocock\skills\tdd` 去查 tag，最后落到 `skill_not_found`——报错点名的是「技能不存在」，不是「键写错了」。

决定：**规范形只有 `/`**。git tag 用 `/` 表示层级，换成 `\` 会在跨平台与 git 语义上出事；登记簿、JSON、TOML 里 `/` 不用转义；macOS / Linux 的 `store` 路径本来就是 `/`；`add` 已按 `/` 校验。

待做：

1. 抽一个共用的键校验器（core 内一处），所有命令的 `<skill>` 入参都过它：非空、`/` 分段、每段禁 `\` / `:` / 空段 / `.` / `..` / 版本形状；不合规报新错误码，并点名「多级键用 `/` 分段」。
2. `add` 的技能名（末段）复用同一个校验器，补上现在只校验前缀的那几条。
3. 不做 `\` → `/` 的静默归一：同一个概念只留一条规则，免得 `add` 拒绝、`use` 却接受。

> 状态：⬜ 未实现，排期未定。

### 8.6 检索：内置 rg 引擎

现状：找技能只有 `fsh list` 一条路，而它每行都带最新版本与发布时间，等于逐键查 git；搜内容（正文、`references\`、`agents\` 配置都算）没有入口，AI 只能自己对 hub 跑 `rg`，拿到的是文件路径而不是技能键，还绕过了 `.lock` 与登记簿。

想法：`fsh search`，把 ripgrep 的检索能力装进进程——依赖 `ignore` 与 `grep` crate，不起外部 `rg.exe`，单 exe 不变。参数面先与 rg 对齐、不预先裁剪，fsh 只补 `--skills` / `--tags` / `--tag` / `--limit` 四样；作用域恒为 hub 根，归档技能因无工作副本天然不进检索。命令契约、输出与退出码见 §3.1。

动工前必须解决：

1. 与 `list` 的重合：`--skills` 一旦给出同一份清单，`list` 是退役还是保留为薄别名，两处同义会让 AI 不确定调哪个。
2. glob 与 ignore 的优先级：rg 的 `-g` 能显式放行被忽略的路径，照抄就能搜到 `.lock` 与 `logs\`；继承 rg 语义，还是钉死「ignore 永远优先、glob 只能收窄」，需要一条明确取舍。
3. 参数面的裁剪记录：全量对齐后哪些 flag 实测无用，要留一个记录位，否则没人敢删。

> 状态：⬜ 未实现，排期未定；动工前先走规格流程。

### 8.7 exe 占用更新协议

现状：更新程序只有一条路——关掉 GUI，把新 exe 复制到旧路径。Windows 会锁住正在运行的 exe：不能删、不能覆盖写，开着程序复制会拿到共享冲突（构建时的 `LNK1104` 是同一类锁）。没有自更新器，所以这条协议眼下没有调用者。

想法：三步换掉自己——把运行中的 exe **改名**（重命名不被禁止），把新 exe 写到原路径，下次启动时删掉改名后的旧 exe。不用 `PendingFileRenameOperations` 这类要重启才生效的机制。

动工前必须解决：

1. 调用者优先：先有自更新或一键升级，协议才有入口；先单独写这段就是没有调用者的死代码。
2. 回滚窗口：改名成功后写新文件失败，必须把旧名改回原名，且不留半份文件。
3. 安全软件：部分策略会对「重命名运行中的 exe」告警，失败文案要指到「关闭程序后手动替换」，不能只抛原始错误。
4. 删旧时机：启动时删一次，失败就留着等下次，不为它加后台进程或轮询。
5. 日志：成功记一条 INFO（路径进字段）；删旧失败记 WARN，可恢复不报 ERROR。

> 状态：⬜ 未实现，排期未定；等自更新或一键升级排上再动。

### 8.8 入库来源：skills.sh 寻址

现状：`fsh add <dir>` 只吃本地目录，`--prefix` 只管键的组织前缀、与来源无关。装一个上游技能得先自己 clone 到本地，多一步，还要求机器上有 git——而 fsh 的立场是不依赖用户装 git，`git2` 已静态链进 exe，克隆能力本来就在。

想法：入参先按 skills.sh 的寻址形状适配——`owner/repo` 简写、完整仓库 URL、仓库内子目录 URL（`…/tree/<分支>/skills/<名>`）、任意 git URL；本地路径保持现状。一个仓库常有多个技能：先 `--list` 看清单，再 `--skill <名>` 选（`*` 全要）。来源只决定"从哪拿"，键仍由 frontmatter 的 name 末段加 `--prefix` 决定。

动工前必须解决：

1. 临时克隆与清理：浅克隆到 hub 外的临时目录（`git2` 已有网络能力），失败要把临时目录整份删干净，不留半个工作副本。
2. 多个 `SKILL.md` 的选取：`--skill` 按 `name` 匹配；重名或未命中要回可用清单，不能只报"找不到"。
3. 默认前缀：从 URL 自动补组织名当键前缀（`owner/repo`）看着顺，但会把"名字唯一来源 frontmatter"这条规则撕开一道口；倾向前者不做，前缀仍旧只由 `--prefix` 给。
4. 凭据边界：公开仓库之外先报 `auth_not_supported`，私库凭据留给 M3 的凭据体系，不在 `add` 里各造一套。
5. zip 来源：没有网络与凭据问题、解压即用，但和 git 来源是两条路，先不做。
6. `--list` / `--skill` 不能只长在 URL 分支：本地目录同样适用，否则两条入参各半套能力。
7. 许可与体积：入库前要不要拦超大仓库或没有许可声明的仓库，先只记事实、不设闸。

> 状态：⬜ 未实现，排期未定。

### 8.9 版本切换原子化与批量升级

现状：`use` 只做首次铺装——登记簿已有该技能记录就拒绝，所以换版本只能 `unuse` 再 `use`，GUI 上是三步（解除 → 使用… → 选版本）。中间任何一步失败，项目里就留下"已解除、没装上"的断链，只能手工收拾。

想法：把"换版本"做成一次要么成功要么不动的操作，另带两个衍生能力：跟最新 ↔ 固定版互转、项目内所有固定版技能批量升到最新（回答"我落后几个版本"）。

动工前必须解决：

1. 命令形状：新命令（如 `fsh upgrade`）还是让 `use` 对已有记录改走"替换"语义。后者把首次铺装与换版本压进一条命令，幂等与报错都要重排。
2. 同路径换入口：新版本落点与旧的一样（技能名不变），不能"先铺新再删旧"，只能"旧入口改名占位 → 新入口建在原路径 → 删旧占位"，回滚时把旧链接还原；与 §8.7 是同一路数。
3. 作业清单与预演：现有写操作靠"预演清单 + 锁内重放"，换版本要给出同一份清单（旧入口、新入口、登记变更），否则预演与实跑会分叉。
4. 批量升级的判定：哪些算落后（登记版本低于最新 tag）、归档技能跳过、部分失败是整批回滚还是逐条报告。
5. GUI 只是入口：版本页与项目页各放一个按钮可以，语义全部在 core，不许前端拼两步。

> 状态：⬜ 未实现，排期未定。

### 8.10 doctor --scan 黑链接排查

现状：doctor 七项只查 hub 内部与登记簿可达性。磁盘上"指向 hub 但登记簿没有"的落点（黑链接）没有任何入口能发现——手工 `use` 过、`projects.toml` 被删或换机器恢复、项目目录被整体拷贝，都会留下这种没人认领的入口。

想法：`doctor --scan` 把落点扫一遍、列出黑链接；沿用 doctor 的定位，只报不动手，清理留给显式操作。

动工前必须解决：

1. 扫描范围必须显式：黑链接恰好不在登记簿里，只能按 agent 表的目录清单去 stat；八十多个内置 agent 乘项目数，全盘扫会很慢。先只支持显式给目录（`--scan --project <dir>`），不做全局 fan-out。
2. 归属判定：链接指向 hub 但属于别的技能算不算黑链接；copy 落点没有 reparse point，只能按"目录存在且登记簿没有"判，要接受一定误报。
3. 项目与全局两侧一起扫，否则"全局装了但登记丢了"照样看不见。
4. 输出形状：沿用 doctor 的三态检查（ok / warn / fail）还是另起一份清单；黑链接该算 warn 还是 fail。
5. 修复动作：本期只报；要不要 `--fix` 删除黑链接留到后面。

> 状态：⬜ 未实现，排期未定。

### 8.11 GUI 撤回只支持单个项目

现状：GUI 的解除入口只认一个目标——单个项目；全局用法要撤只能走 CLI 的 `fsh unuse --global`。项目页与技能详情使用页共用同一个解除流程，桥命令收 `key`、一个 `project` 与要撤的 agent 名单。

想法：GUI 的解除与 CLI 的 `unuse` 用同一套目标集合（可选一个全局目标 + 零到多个项目目标），对话框形如「使用…」但方向相反。

动工前必须解决：

1. **桥命令形状**：解除命令现在收单个 `project` 与 agent 名单，还差全局开关与项目列表，要改成与使用命令对称。
2. **多项目的失败面**：core 的口径是「先检查全部目标，任一不合格整次不动盘」，GUI 沿用同一条，不在前端拼多步。
3. **全局侧的可视**：GUI 现在没有全局用法的列表（项目页只列项目记录），要撤全局得先有地方看见它，否则「装到全局」变成只能装不能看。
4. **确认文案**：跨多个目标时要说清撤哪几处、留哪几处，不能只写一句「撤回全部落点」。

> 状态：⬜ 未实现，排期未定。
