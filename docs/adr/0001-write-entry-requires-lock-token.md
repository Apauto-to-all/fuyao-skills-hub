# 写入口必须持锁令牌（capability token）

## 背景

fsh-core 的全部写路径（技能管理、hub 装配、项目使用）依赖进程级文件锁互斥，但「先取锁再动盘」只是各入口手写 `let _guard = write_lock(...)` 的约定——新增写入口时忘取锁不会编译失败，只会在线上变成数据竞争。

## 备选

- 维持约定 + 文档说明：已证明随调用点增长而脆弱，放弃。
- 全量两段化（先产动作清单再执行）：改动面远超收益，放弃。

## 决策

`lock` 模块提供 `WriteToken`：字段私有，仅 `write_lock` 可构造，持有即证明当前进程持有 hub 全局写锁。写路径的内部共享函数一律以 token 为参数，「忘锁」直接编译失败。锁内顺序不变量（先锁、再读登记簿、后写盘）写在 token 的类型文档上。写入口统一经 `git::open_hub_for_write` 取锁并开仓，token 随写骨架的 `Ctx` 传到落盘段，入口自己不再碰锁。

## 理由

- 锁的持有与否由类型表达，编译器替人守住这条约定；新增写入口只有一个姿势可抄。
- 取锁与开仓合成一处：判定先于取锁，未建 hub 的根上不留锁文件，锁内复判不留可写窗口。
