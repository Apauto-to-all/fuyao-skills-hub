# 预演走 dry_run 布尔单入口

## 背景

写操作一度长出 `*_dry` 双生函数，CLI 在分发处挑分支、各自拼 JSON 包络；gc 与 init 却是另一种形状——单一入口收 `dry_run: bool`。两套形状并存，锁姿势各自维护：7 个 dry 双生全部以 `lock_and_open` 起手，预演本应只读却抢全局写锁——另一进程写 hub 时，`--dry-run` 被误报「锁被占」。

## 备选

- 保留双生函数：调用方少看一个参数，但每个操作维护两份签名与两份锁姿势，双生漂移正是本次锁 bug 的成因，放弃。
- 返回携带 actions 的结果枚举（Real/Dry 两态）：类型上强制区分，但 CLI/GUI 都按 serde 形状直出消费，枚举只多一层人人要 match 的包装，放弃。
- 单入口收 `dry_run: bool`、返回胖结构：与 gc/init 统一成一种形状，锁姿势只写一遍，采用。

## 决策

每个写操作一个入口，尾部收 `dry_run: bool`。预演走只读开仓、不取写锁，返回动作清单；实跑走 `lock_and_open` 并持 `WriteToken`（忘取写锁仍是编译错误，见 ADR-0001）。返回 `*Outcome` 胖结构：实跑填业务字段、预演填 `dry_run: true` 与 `actions`，空字段 `skip_serializing_if` 略去，serde 直出与旧信封逐字一致。

## 理由

- 锁策略内联在函数开头的 `if dry_run` 分支，跟随 gc 的现形，不引入 Session/上下文对象。
- 包络由结构体字段塑形，CLI 分支拼接删除，`--dry-run` 输出形状全命令一致。
- 新增写操作只有一个模板可抄，双生漂移在结构上不可再现。
